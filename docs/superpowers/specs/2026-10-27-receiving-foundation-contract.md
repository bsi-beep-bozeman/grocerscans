## 1. Decision and boundary

Choose native browser IndexedDB through `idb_shim 2.10.1+1`, Android SQLite through `sqflite 2.4.5`, and per-record AES-256-GCM through `cryptography 2.9.0`. Promote already locked `web 1.1.1` to a direct dependency for lifecycle/storage browser APIs; retain its version. Keep one platform-neutral DraftStore interface, with separate production adapters and a fake used only by unit tests. No preferences-only, in-memory, browser localStorage or silent fallback store may show a successful durable save.

Choose an opaque server staff-session secret with an eight-hour absolute lifetime, online PIN re-verification to renew, and a server-held draft key per org/branch/device/original-actor partition. Keys and session secrets exist only in client memory while unlocked. This eight-hour bound is a new engineering choice for implementation acceptance, not an existing product policy or measured behavior. The already accepted five-minute inactivity/background/person-switch lock remains unchanged.

S2-A implements identity, safe receiving metadata, encrypted local drafts, sealing and attributed partition recovery. It creates no receipt, stock, catalog request, approval, scanner behavior or operational stock action. Queue upload/reconciliation interfaces have a disabled production transport until S2-B. UI must say **Saved on this device**, never stock received or synced. Admin S1 setup continues through its existing gate. Individual staff operational login, viewer and supplier dashboards remain out of A; they receive a clear unavailable-workspace state, not inferred kiosk authority.

## 2. Identity and session protocol v1

All public RPCs use JSON object inputs/outputs with `contract_version:1`, bounded size and strict field/type validation. Authenticated transport identity comes from verified Supabase JWT `sub`; require a valid numeric unexpired `exp` on every call. Never trust tenant/role claims or caller-supplied actor IDs. TLS is required outside explicitly approved loopback synthetic testing. PIN/session/key material must be excluded from request/response logging, tracing, exception text and analytics.

### Account resolution

`get_receiving_context_v1()` returns `{contract_version, server_time, kind, org_id, branch_id, branch_name, device_id, device_label, timezone}` for exactly one active kiosk mapping with no staff or supplier profile on the same auth subject. Reject conflicting mappings even if one is inactive; the mixed identity needs administrator correction. Check referenced org/branch consistency explicitly: the retained foreign keys alone do not enforce it. Existing branches have no active column; do not invent an active predicate or quietly add one. A missing branch is unavailable.

For an unambiguous active administrator, return only `{contract_version, server_time, kind:'admin_setup'}` and use the S1 allowed-branch mechanism. Other identities return `{contract_version, server_time, kind:'unavailable'}`. Do not enumerate staff, disclose PIN state, or use legacy `currentProfile()` as an authorization result.

### Verification, cooldown and concurrency

`begin_staff_session_v1(p_pin text)` accepts exactly 4–6 ASCII digits, as a string. It derives the device and scope. Eligible actors are active same-org, same-branch `role='staff'` profiles, with no conflicting kiosk/supplier identity; `is_shift_lead` may be true. Admins use S1; viewer, supplier and historical manager are denied. Match every eligible candidate and require exactly one match. Zero/multiple matches have the same public denial. No candidate list or attempt-specific identity is returned.

Create one permanent attempt row per device using INSERT ON CONFLICT DO NOTHING, then lock it FOR UPDATE before checking the counter. Never delete this row to reset it. Lock order for these endpoints is device attempt row, device row, relevant staff rows ordered by UUID, session/vault rows. Recheck auth expiry, identity and branch after waiting. Administrative changes must either take compatible row locks or be detected by the final recheck. [PostgreSQL row-lock behavior](https://www.postgresql.org/docs/15/explicit-locking.html) supports serialization; actual race behavior still needs tests.

On each completed invalid or ambiguous PIN attempt, increment `failed_count`; malformed PIN from a resolved authenticated kiosk counts too. The fifth failure sets `blocked_until = clock_timestamp() + interval '5 minutes'`. During cooldown, deny before PIN work, do not increment or extend it, and return `retry_after_seconds = ceil(max(0, blocked_until-server_time))`. At expiry, atomically reset and process the new attempt. Success resets failures and revokes previous device sessions before issuing the new session. Network retries of verification are new attempts; never automatically retry a PIN request. Account sign-out, client reinstall and restart do not reset the server row. A new device credential is provisioning authority, not a client workaround.

Expected denials return a normal RPC envelope, so counter updates commit: `{contract_version:1, ok:false, error:{code:'verification_failed'|'cooldown'|'unavailable', retry_after_seconds:int|null}}`. Do not RAISE an exception after incrementing and thereby roll the counter back. Unexpected database failure rolls back the whole transaction and returns an unsaved/service-unavailable result; no session or key is released. Audit storage must not contain PINs, hashes of attempted PINs or raw secrets. Infrastructure rate/DoS controls are a separate release requirement, not proof supplied by this counter.

On success return `{contract_version, ok:true, server_time, session:{id, secret, issued_at, expires_at}, context:{org_id,branch_id,device_id}, actor:{id,display_name,is_shift_lead}, vault:{id,key_version,key_b64}}`. Generate a cryptographically random 32-byte session secret on the server; persist only its SHA-256 digest, plus session UUID, subject, org, branch, device, actor, actor PIN-change timestamp, issued/expires/revoked timestamps. Use the retained pgcrypto extension's random generator; [pgcrypto documentation](https://www.postgresql.org/docs/15/pgcrypto.html). The vault key is different random material and never the PIN or session secret.

### Lifetime, revocation and lock

Subsequent receiving RPCs take `p_session_id uuid, p_session_secret text`. Every call rechecks JWT expiry, session digest/absolute expiry/revocation, original subject/device/scope, active staff role, PIN-change timestamp and current role flags. Role/PIN/device/scope changes invalidate the old session. End/denial does not delete drafts or vault keys. `end_staff_session_v1(id,secret)` is idempotent for that device's session; successful re-verification always revokes its predecessor. Do not retain or replay bearer proof in local queue records.

Absolute expiry is issued-at plus eight hours, never sliding with background polling or token refresh. No silent renewal; another successful PIN request issues a new session. Client uses server time plus elapsed monotonic time, locks on absolute expiry, and fails closed if its time reference is uncertain. Supabase JWT expiry blocks network calls; refreshing the same account JWT does not unlock a locked staff session or reset its absolute lifetime. An active offline client may capture only until staff-session absolute expiry and the accepted local lock conditions; expired transport JWT never grants online access.

Lock on 300 seconds without meaningful human input, any Flutter lifecycle state other than resumed, web visibility loss/pagehide/blur, account change/sign-out, switch-person, session denial or local integrity fault. Resume never automatically opens the vault. Cover nested dialogs and navigation. Increment an in-memory generation before clearing state; late RPC/decryption completions from an earlier generation must be discarded and must not unlock or display success. Offline lock is immediate locally; remote session revocation is best effort when connected. A stolen bearer may remain valid until server expiry/revocation: the server cannot observe an offline background event. This is an explicit residual threat, not a claim of remote instantaneous lock.

Allow one active browser tab for this workspace using an exclusive Web Lock, and cross-tab lock notification without secrets. A second tab cannot unlock/capture; if required APIs are unavailable, disable the durable workspace with an explanation. Local multi-tab protection is not a substitute for server revocation. A second physical device retains its own device-scoped session; it cannot open this device's local partition.

## 3. Exact safe receiving read DTOs

`get_receiving_catalog_v1(session_id,session_secret,query,after_id,limit)` requires a session and returns `{contract_version,server_time,context,active_setup_version_id,active_setup_revision,items,next_after_id}`. Context is exactly org/branch/device IDs. Query is `{kind:'upc'|'sku'|'name'|'all',value:string}`; 128 characters maximum, name query minimum two characters, limit 1–100 (default 50), cursor a validated UUID. UUID-ordered keyset pagination is scoped to the query and current org; do not treat multiple pages as a consistent snapshot. UPC/SKU compare exact strings with leading zeroes preserved. Parameterize queries and escape LIKE metacharacters for name search. Missing/ambiguous matches require explicit selection. `all` is for bounded incremental cache fills, not an unlimited response.

Each item contains exactly `{id,upc,sku,name,category_id,category_name,default_supplier_id}`. Nullable identifiers stay null; no financial columns, timestamps pretending to be revisions, email/contact data or arbitrary joined records. Validate supplier/category tenant before returning IDs. Legacy product/category/supplier tables have no activity/revision fields. Do not manufacture `active:true` as receiving eligibility: eligibility comes from current active setup and validated references.

`get_receiving_policy_v1(session_id,session_secret,product_id)` returns `{contract_version,server_time,context,product,setup,unit,pack,requirements,entry_modes,label_profile,expiry,receiving,locations,suppliers,readiness}` with these exact nested fields:

| Object | Allowed fields and meaning |
|---|---|
| product | Same catalog item above. No arbitrary product-row serialization. |
| setup | `version_id`, `revision`, `timezone` (from the active configuration), `preset_version_id` nullable. No draft/admin audit history. |
| unit | `code` in the existing enabled setup unit codes, `precision` integer 0–3; null when incomplete. |
| pack | `name`, `count` decimal string; null when incomplete. No inferred conversions. |
| requirements | `supplier`, `reference`, `lot`, each required/optional/unknown. |
| entry_modes | Array restricted to existing setup manual/barcode/sku choices; this slice exposes manual capture only. |
| label_profile | Existing validated setup value or unknown; no scale-format guessing. |
| expiry | `mode` printed/calculated/unknown; `rule` null or `{value,unit,policy_reference}` projected from effective expiry rule. Computed confirmation remains disabled in A/B. |
| receiving | `location_ids`, `hold_location_id` nullable, `exception_role` unknown/lead/admin, projected from active ReceivingSetup and checked against current same-branch locations. Null if no active setup. |
| locations | Array `{id,name,revision}` of active same-branch setup locations. No free-text legacy default treated as a validated location ID. |
| suppliers | Array `{id,name}` for same-org suppliers, capped at 100; if more, return a separate paged supplier lookup requirement rather than truncate invisibly. |
| readiness | `can_capture_draft:true`, `can_confirm:false`, `blocking_codes` string enum array for setup_missing, unit_missing, pack_missing, requirement_unknown, location_missing, policy_missing, invalid_reference, unsupported_mode, confirmation_not_implemented. |

Use the active setup version and revalidate referenced preset/location activity. Resolve inherited policy with the same semantics as S1 without changing S1 data. If no active setup exists, return `setup:null`, nullable policy objects, empty reference arrays and `setup_missing`; allow only an incomplete manual draft. No default timezone, unit, supplier or safety policy is invented. Limit the encoded response to 256 KiB; oversize yields `catalog_too_large` and no misleading partial successful snapshot. A paged supplier endpoint, if needed, is part of a reviewed contract amendment before code, not an unlisted public API.

Safe cache entries contain only these DTOs, fetched time, context, and setup revision; encrypt them in the same actor partition. Show last-fetched time offline. New product/config changes are not inferred from stale cache. No unrestricted batch detail in A. Errors after session establishment are allowlisted: unauthenticated, session_expired, session_revoked, unavailable, invalid_request, setup_missing, catalog_too_large, storage_unavailable, conflict; include a safe field path where useful, never submitted secrets or SQL text.

## 4. Legacy access closure required before enabling A

Source observation only: seven retained migrations define broad RLS read paths, `current_staff()` returning a composite staff row, authenticated kiosk PIN RPC execution, and five authenticated reporting views. Returning a smaller new DTO leaves those alternate entry points. No live ACL/catalog snapshot was taken; default/inherited grants can differ from explicit source statements.

Selected source proposal is RPC-only client access for this bounded foundation. In a NEW migration, explicitly revoke all table/view privileges from PUBLIC, anon and authenticated for these retained objects: `orgs`, `branches`, `staff_profiles`, `kiosk_devices`, `categories`, `suppliers`, `products`, `batches`, `purchase_orders`, `po_lines`, `receiving_events`, `alerts`, `rounds`, `round_items`, `temp_logs`, `audit_log`, `supplier_profiles`; plus `v_upcoming_shipments`, `v_stock_by_product`, `v_supplier_scorecard`, `v_waste_recovery`, `v_alert_response_times`. The eight S1 setup tables remain denied as already designed. No direct sequence permission for these tables may bypass the boundary. Do not change storage/auth/system schema grants.

Revoke PUBLIC/anon/authenticated execution of ALL overloads of retained legacy functions `current_staff`, `current_app_role`, `current_org_id`, `current_branch_scope`, `is_admin`, `is_manager_or_admin`, `is_kiosk_device`, `is_supplier`, `current_supplier_id`, `set_staff_pin`, `kiosk_verify_pin`, `_assert_kiosk_actor`, `kiosk_log_batch`, `kiosk_resolve_alert`, `kiosk_start_round`, `kiosk_add_round_item`, `kiosk_complete_round`, `kiosk_log_temp`, `refresh_alerts`. Resolve signatures from the explicit migration inventory and review against pg_proc under a future approved read. Do not revoke every function in public indiscriminately: extensions and S1 internals need care. Retain the six S1 public setup RPC grants and their administrator guards. New internal helpers and private state have no client grants. New public session/read/recovery RPCs are explicitly granted to authenticated only and internally authorize every call. SECURITY DEFINER functions have a fixed trusted search_path, schema-qualified objects and no dynamic caller-supplied SQL; see [Supabase function guidance](https://supabase.com/docs/guides/database/functions).

This intentionally removes legacy direct access for all authenticated application roles, including viewer/supplier/legacy admin tooling. S1 RPCs remain usable; any other deployed consumer is unknown. Applying these changes requires exact-target permission approval plus consumer inventory; do not label this a transparent compatible deployment. No hosted change is authorized. Realtime and API joins must be tested as alternative access routes. A database-role ACL diff and actual API denials are prerequisites for operational acceptance; source review cannot certify isolation.

## 5. Encrypted local store and key custody

Production browser database `shelflife_drafts_v1` has `vault_meta`, `drafts`, `cache`, `migration_journal` stores. Android database `shelflife_drafts_v1.db` has corresponding tables and unique indexes. Partition identity is org/branch/device/original actor, resolved server-side; local record keys use a random server vault UUID. The outer record contains only `{envelope_version,vault_id,key_version,record_id,revision,nonce_b64,ciphertext_b64,tag_b64}`. Status, product, people, operation IDs, payloads and queue metadata are encrypted. Outer metadata leaks record counts, sizes, revisions and opaque IDs; do not claim zero information leakage.

Use AES-256-GCM with a fresh secure random 96-bit nonce on every encryption, 128-bit tag, and deterministic UTF-8 AAD encoding of envelope version/vault/key version/record ID/revision. Never reuse nonces on retries; persist the already encrypted envelope when retrying a transaction. Validate context and IDs again inside decrypted data. Reject malformed sizes, unknown versions, authentication/tag errors or partition mismatch. No unauthenticated fallback. The package uses Web Crypto in browsers and Dart implementation otherwise without the optional native acceleration plugin; [AES-GCM API](https://pub.dev/documentation/cryptography/latest/cryptography/AesGcm-class.html).

Server table `private.receiving_vault_keys` stores random 256-bit keys with vault UUID, partition tuple, key version, created/retired status. The schema is not exposed to PostgREST and has no client USAGE/table grants. SECURITY DEFINER RPCs release only the authorized partition key after PIN verification; subsequent session checks never mint an unrelated actor key. Persisting these server-side keys is necessary to reopen local ciphertext after restart. Keys survive PIN change and session revocation; releasing them requires the new valid PIN/session. Do not delete/rotate keys simply because an actor is inactive; recovery may still be needed. Rotate only with a separately approved protocol that retains old keys until known local records have been re-encrypted; offline device inventory makes automatic deletion unsafe.

Private schema records are `receiving_device_attempts` (device PK, failed_count0–5, blocked_until), `receiving_staff_sessions` (session PK and fields in section2; unique live session per device), `receiving_vault_keys` (unique partition/key_version, key length32), `receiving_recovery_grants` (grant PK, original partition, recovering actor, reason, issued/expires and authorizing session), and append-only `receiving_identity_audit` (event UUID, server time, kind, scope, actor/session/grant references; no keys/PINs/digests). A session issue/recovery grant and its audit commit together. Existing org/branch/device/actor consistency is checked transactionally, with restrictive deletion behavior for retained keys/grants. Default privileges for the new private schema deny client access; RLS is enabled without client policies. Do not add deletion cascades that silently destroy recovery keys. A single live-session invariant uses explicit revocation status, not a time-dependent partial index predicate.

**Custody decision:** this initial design trusts the database operator and protected database backups; server keys are stored as private bytea, not claimed encrypted against database administrators or stolen raw server backups. Production key wrapping, managed KMS, retention and backup access are a release decision before hosted use. There is no new KMS dependency or credential change in A. Client at-rest confidentiality protects a copied local database without its server keys; it does not protect XSS/malicious same-origin code, rooted devices, debug memory inspection, or a compromised server. PIN-derived encryption is rejected because 4–6 digits are enumerable. Persisted web CryptoKeys or Android secure-storage auto-unlock are rejected because they do not independently enforce fresh staff verification.

Keep key bytes, plaintext cache and staff proof in memory only. Clear references and overwrite owned mutable buffers on lock as best effort; Dart/JS garbage collection prevents a guaranteed total-memory wipe. No service worker/background upload, persistent auth cache hook or Supabase token refresh may reload a vault. Supabase account persistence is separate existing behavior; its credential alone must not release staff draft keys. For production response paths require no-store handling and verify no caching/logging at gateway/client; this is a deployment gate, not an applied configuration here.

### Save, migration and failure contract

The decrypted draft schema is `{schema_version:1,draft_id,operation_id,org_id,branch_id,device_id,original_actor_id,captured_at,updated_at,kind:'receiving_draft',payload,known_setup_version_id,known_setup_revision,dependencies,state,attempt_count,next_attempt_at,last_outcome,recovery}`. Payload allowlist is `{product_id,entered_identifier,entered_name,quantity_text,unit_code,receipt_date,expiry_date,expiry_basis,supplier_id,delivery_reference,lot,location_id,earlier_date_reason,notes}`; unknown/missing values stay null. Text limits: identifier128/name120/quantity32/reference120/lot120/reason1000/notes1000 UTF-16 units. Dates are ISO date strings or null; timestamps UTC. Maximum encoded plaintext record64 KiB; reject oversized input, keep form. Maximum1000 local drafts or20 MiB ciphertext per installation, whichever first; fail save honestly and preserve existing drafts. Cache may be pruned; unsynced drafts never are.

Encrypt outside a database transaction. In one transaction compare expected revision and write the complete ciphertext record containing draft, stable operation ID and queue state. Await transaction completion, not a request's initial success, before displaying saved. On browser use only native IndexedDB factory; on Android use sqflite transaction object for all operations and journaled SQLite with synchronous FULL requested/verified. No file append or independent preference updates. A conflicting editor retains its form for explicit review; never overwrite a newer revision. App crash/reload should retain the last committed record; power loss/browser eviction is not an unconditional guarantee. [IndexedDB transaction limits](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction) and [browser persistence limits](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) are acceptance constraints.

Auto-save after a short input debounce and on explicit Save; never promise unsaved keystrokes survived termination. On lock synchronously conceal, invalidate callbacks and clear visible data; an already encrypted queued write may finish without reopening the screen. Attempt to seal the latest edit promptly while key is held, then drop keys; a failed seal retains the last committed draft and reports possible unsaved changes after re-verification. Lock never waits for network or indefinite I/O. On quota/I/O failure retain the last good record, show Not saved, and permit retry during the active session. If backgrounding prevents persistence, do not hide that loss behind a saved badge.

Request browser persistent storage after user interaction and display whether it was granted. A refusal does not make an in-memory fallback acceptable. Disclose local-only loss on eviction/site clear/private-session end; a fully erased origin cannot reliably remember that records once existed. On reopen online verification retrieves existing vault identity but never recreates missing records or calls them synced. Android update must preserve DB; clear-data/uninstall/device loss can remove it. Exclude this database from cloud backup/device transfer using narrowly scoped Android backup-rule source changes, preserving other manifest settings; [Android backup behavior](https://developer.android.com/identity/data/autobackup). This is not a substitute for actual device restore testing.

Initial schema is1; no old production receiving store is known. For future upgrades, additive physical schema changes use native upgrade transactions. Encrypted payload migration uses per-record shadow values plus a journal and atomic generation pointer swap only after validation/count checks. Keep the old generation until successful reopen; quota/interruption retains it. Never delete/reset on an unknown newer version. Tag/corruption failures quarantine only the affected record without displaying plaintext; keep ciphertext for an explicitly authorized recovery procedure. Database-open failure never creates a replacement over the original. No automatic export, purge, or bulk re-encryption is authorized by a normal sign-out.

## 6. Recovery and queue semantics

Original-actor unlock releases only their partition. An ordinary replacement actor cannot list names, preview or open other partitions. For an absent/disabled original actor, same-branch active staff with current `is_shift_lead=true` can request **Recover this person's drafts on this device**. An unambiguous active admin can select an allowed same-org branch and device through an explicit admin recovery path. Both require online recent authentication: lead PIN verified within five minutes; admin Supabase password reauthentication within five minutes, not token refresh alone. Admin implementation in A may remain unavailable until an approved recent-auth proof is specified; it must not fall back to ordinary admin JWT age. The fully specified initial recovery path is lead PIN; admin recovery is a denied extension, recorded as a remaining A coverage limitation.

`recover_receiving_partition_v1(session_id,secret,original_actor_id,reason)` authorizes the current lead against the requested partition's derived device/org/branch, requires a trimmed reason1–1000 units, locks/rechecks current role, and atomically appends an audit grant before returning `{recovery_id,vault_id,key_version,key_b64,original_actor_id,recovering_actor_id,granted_at,expires_at}`. Expiry is the earlier of session expiry and five minutes. A repeat creates a new audited grant (no automatic retry); failure to write audit releases no key. This deliberately authorizes all drafts in that actor's partition on this device, not one selected item: a partition key can decrypt all its records. UI must disclose that scope before confirmation. Disabled original actor is allowed for recovery, but original ownership and same-scope references must still exist; deleted/inconsistent actor/branch is a blocked administrative recovery case, never auto reassignment.

Client opens the partition in a distinct recovery workspace until grant expiry, preserves `original_actor_id`, and writes `recovery:{recovery_id,recovering_actor_id,reason,granted_at}` inside each adopted draft. No impersonation or receipt submission. Once opened, key expiry cannot cryptographically retract copied plaintext; compliant client drops it on expiry/lock. Later S2-B must validate the recovery grant/current lead and re-review intent on submission. No retroactive claim that the server authenticated every earlier offline edit.

Local states are Editing, Local saved, Waiting for sign-in, Waiting for dependency, Ready, Sending, Retryable failure, Conflict, Rejected, Confirmed and Storage failure. In A, only local/save/sign-in/dependency/conflict/storage states are reachable through real transport; tests may model future states. A never calls legacy `kiosk_log_batch`. Future B freezes payload and operation key before first send; timeout/response loss keeps that pair, reconciles before retry, then bounded exponential retry (1,2,4,8,16 seconds; five attempts then manual). Rejection/config conflict stops automatic replay. A reviewed successor gets a new operation ID only after outcome is known and no stock was committed; uncertain operations remain frozen. Confirmed requires a durable server receipt reference, not a successful local save or catalog decision.
