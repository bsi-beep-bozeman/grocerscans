## Two-connection concurrency procedure

Use a separately approved disposable fixture containing an active administrator, organisation, branch, ready draft revision D, active pointer revision A, active preset revision P and location revision L. Use fresh operation UUIDs except for explicit retry cases. Set valid JWT claims independently on each connection; never persist credentials in evidence. Each race uses explicit `BEGIN` in A and B. Set B's `lock_timeout` to a bounded 5 seconds when checking blocking; a timeout must roll back B before retry. Fixtures for this procedure must be committed for cross-connection visibility, then removed by resetting the disposable database after evidence capture.

1. A saves with expected D and remains uncommitted. B saves a different payload with expected D: verify B blocks on the organisation row. Commit A, retry B after any timeout; expect PT409 and no additional draft revision/audit/operation. Repeat with identical operation UUID and identical request: B returns A's exact stored response, with one audit and operation. Same UUID with changed configuration or action must produce PT409.
2. A activates with D/A and stays uncommitted. B activates with D/A using another operation: verify blocking, then PT409 after A commits. Exactly one new immutable version and one pointer increment exist. Repeating A's identical operation returns its original response.
3. A saves D+1 while B activates D: whichever obtains the organisation lock first wins. If save wins, activation fails PT409. If activation wins, its snapshot contains exactly D; subsequent save creates D+1 without altering that snapshot.
4. A edits/deactivates the referenced preset or renames/deactivates the location; B activates. Verify serial execution. If reference mutation wins, B recomputes readiness using the new authoritative state and rejects activation when no capability remains ready. If activation wins, its reference names/effective policy/readiness remain byte-for-byte unchanged after reference mutation.
5. Two edits of P, or two renames of L, must yield one success and one PT409. Race operations against another branch in the same organisation to confirm the same lock order; race distinct organisations to confirm they do not block on the setup organisation lock.
6. Hold A's organisation lock; revoke/deactivate B's administrator in a third connection, then release A. B must reauthorize after obtaining the lock and fail 42501, including identical-operation retries. Expire B's JWT while blocked: expect PT401. Capture `pg_locks`/wait evidence and statement results, then compare immutable histories, pointer revisions and all inventory counts/row checksums.
7. Start with a committed ready draft and no active pointer. A performs its first activation and holds the transaction before commit. B repeatedly calls `get_store_setup` while A commits. Assert every response using the `assert_active_pair` predicate from the transaction suite: either `active` is null and `active_revision` is 0, or `active.version` equals the positive `active_revision`. Repeat while A publishes a subsequent version; B may observe the old or new pair but never a version paired with another revision. Capture responses around each commit, and parse them through `BranchSetupState.fromJson` when connected application validation is separately approved. The version and revision now come from one joined SELECT; the Chapter 06 race captures and headless DTO results are linked above; browser adapter/reload/restart checks now have October26 evidence.

## Contract and limits

Configuration JSON: schema version exactly integer 1, maximum 256 KiB UTF-8 compact JSON, strict allowlisted keys/types/enums; unknown values and partial draft fields remain legal where the Dart parser permits them. Names/text fields: 120 UTF-16 code units; reason/description/policy references/prerequisites: 2,000. UUIDs canonical hyphenated syntax; optional empty draft references are incomplete selections. Precision: integer 0–3, `each` precision 0; `each` pack count whole. Source/destination whole-each readiness is checked at activation. No product/action is silently enabled. A structurally valid draft may be incomplete but cannot reference another organisation/branch. Activation requires at least one ready capability and no reference errors.

All six RPCs derive authority from the authenticated user, check unexpired JWT `exp`, require exactly one active administrator, deny active supplier/device identity conflicts, and scope branch/entity references. Mutations serialize on the organisation row before entity locks and reauthorize after waiting. The idempotency key is organisation + administrator + UUID; the full action and request JSONB must match. Reference history and active version snapshots are append-only. Baseline branches/categories/products have no activation/revision columns, so the catalog reports `active:true, revision:1`. Names exceeding the wire limit in existing baseline catalog records are rejected rather than silently truncated.

No setup RPC writes batches, receiving, rounds, alerts or the operational audit log. Setup audit is separate. Activation freezes the unmodified configuration plus an internal reference/effective/readiness snapshot. Deactivation never deletes old versions. RLS with no direct-access policies and explicit privilege revocation protects every new table; helper execution is revoked from public/anon/authenticated.

History responses contain the latest 100 scoped audit entries, presented chronologically; all older records remain stored. Required-text readiness uses Dart-compatible Unicode trimming, and numeric input must fit a finite IEEE-754 double. A legacy product pointing to another organisation's category causes a generic validation rejection before catalog disclosure. Source assertions include actual `authenticated`/`anon` privilege denial, revoked-administrator retries, strict invalid payloads with no audit/operation side effects, original reference-mutation retry responses, and rejection of activation after a preset deactivation. These assertions were executed on the disposable Chapter 06 target; the dated evidence distinguishes SQL, concurrency and real Auth coverage from the separately recorded browser checks.

## Rollback

Before applying, preserve an approved database backup and record migration history. If application rollback is needed, disable the setup UI/RPC access while retaining setup history; do not delete immutable production records. Revoke EXECUTE on the six public setup RPCs from authenticated (separate approval required). Existing inventory schema is untouched. A destructive schema rollback is appropriate only for the disposable acceptance database: reset that database from its pre-change snapshot. Never roll back by editing completed migrations or deleting production audit/version rows. Migration installation and rollback execution remain separately gated.
